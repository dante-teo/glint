# Repository Guidelines

## Project Structure & Module Organization

Glint is a macOS app built with SwiftUI, AppKit, and GhosttyKit. Application code lives under `Glint/`, grouped by feature: `App/` for app lifecycle and update wiring, `Chrome/` for shell UI, `Pane/` for terminal surfaces, `Agent/` for agent integration, `Workspace/` for persistence and workspace state, and `Ghostty/` for GhosttyKit management. Resources are in `Glint/Resources/`, including asset catalogs, entitlements, localization, themes, and `Info.plist`. Unit tests live in `GlintTests/`. Release and asset automation lives in `scripts/`; documentation and the static site live in `docs/`. `project.yml` is the XcodeGen source for the checked-in `Glint.xcodeproj`.

## Build, Test, and Development Commands

- `git submodule update --init --recursive`: fetch the `ghostty` submodule required by GhosttyKit setup.
- `scripts/setup-ghosttykit.sh`: download and verify the matching prebuilt `Vendor/GhosttyKit.xcframework`.
- `xcodegen generate`: regenerate `Glint.xcodeproj` after changing `project.yml` **or adding/removing source files**. XcodeGen resolves glob patterns at generation time, so new `.swift` files won't appear in the Xcode project until you regenerate.
- `xcodebuild test -project Glint.xcodeproj -scheme Glint -configuration Debug -destination "platform=macOS" CODE_SIGNING_ALLOWED=NO`: build and run the XCTest suite locally.
- `open Glint.xcodeproj`: open the app in Xcode for interactive development.

## Coding Style & Naming Conventions

Use Swift 5.10 conventions with 4-space indentation and clear feature-local organization. Prefer small pure helpers for domain logic, immutable values where practical, and SwiftUI views composed from focused private subviews. Name test files after the behavior under test, such as `AgentKindResolutionTests.swift`, and use direct test method names like `testUnknownReturnsNil`. Keep resources named by product or agent state, for example `CodexWorking.dataset`.

## Testing Guidelines

Tests use XCTest in the `GlintTests` target. Follow red, green, refactor: add or update a focused failing test before implementation changes. Keep tests independent and deterministic; use `@MainActor` for UI or workspace state code that requires it. Run the full `xcodebuild test` command before declaring a change complete.

To unit-test `WorkspaceStore` operations (tabs, splits, pane state), create a `WorkspaceStore()` and override `workspaces` and `selectedWorkspaceID` with test data. The init loads persisted state, but overwriting those two properties replaces it entirely. There are no live surface views in tests, so `focusedPaneLiveCwd()` falls back to the model — this is expected. See `CwdInheritanceTests.swift` for the canonical pattern.

Only apply `@MainActor` to test classes that actually require it (i.e. those calling `@MainActor`-isolated code like `WorkspaceStore` methods). Tests for non-isolated types such as `SleepAssertionManager` should remain unannotated. If a test file would need `@MainActor` for only some tests, split them into separate files — each named after the behavior it covers.

### Pane dim overlay and IOSurface compositing

The unfocused-pane dim wash (`Color.black` in `PaneView.paneBody`) must be **always present** in the ZStack with its opacity toggled (0 when focused, 0.18/0.28 when unfocused). Do NOT convert it to a conditional `if !isFocused { ... }` — that causes the SwiftUI layer to be inserted *after* the `GhosttySurfaceView`'s IOSurface-backed Metal layer is already composited, and the overlay ends up behind the surface (invisible). Keeping the overlay in the initial render guarantees correct Core Animation z-ordering. This applies to any SwiftUI overlay placed above an `NSViewRepresentable` with a GPU-backed layer in a ZStack.

### Split pane focus click propagation

`GhosttySurfaceView` (an NSView) handles `mouseDown` before SwiftUI's gesture system sees the event, so the `.onTapGesture { store.focus(paneID) }` on `PaneView`'s ZStack does NOT fire for clicks on the terminal surface. To propagate focus changes from clicks back to the store, `mouseDown` posts a `glintPaneFocusClicked` notification (same pattern as Esc/Return) with the pane key. The store observes this notification **synchronously** (`queue: nil` + `MainActor.assumeIsolated`) so that `focusedPane` updates before the next `updateNSView` pass can fight back and resign the first responder. Do NOT rely on `.onTapGesture` alone for focus — it only fires for clicks on SwiftUI-rendered areas, not on NSViewRepresentable content.

### Reacting to agent state changes

`paneAgentState` on `WorkspaceStore` is a `@Published` dictionary mutated from ~18 sites (subscript writes, `removeValue`, bulk `filter` reassignment). All mutations trigger its `didSet` hook. To add a new side effect driven by agent state (as `updateSleepAssertion()` does), add a call in the `didSet` — do not scatter calls across individual mutation sites, which is fragile and easy to miss. IOKit is already linked in `project.yml`.

### Agent workspace domain model

`WorkspaceKind` (`.terminal` | `.agent`) and `AgentProvider` (`.devin`) distinguish terminal from agent workspaces. Agent workspaces carry extra fields on `Workspace`: `kind`, `agentProvider`, `committed`, `agentProjectPath`, `agentSessionID`. All default to terminal-safe values (`.terminal`, `nil`, `true`, `nil`, `nil`) so old `state.json` files decode unchanged via `decodeIfPresent`. The encoder omits default values — terminal workspaces produce no extra JSON keys.

**Committed vs uncommitted:** Agent workspaces start `committed = false` (hidden from sidebar, stripped from `persist()`). Calling `commitAgentWorkspace(_:)` after the user sends their first message sets `committed = true`, making the workspace visible in `activeWorkspaces` and persistent across launches. Terminals are always committed.

**Auto-cleanup:** `selectWorkspace(_:)` silently removes the old workspace if it was uncommitted (user navigated away without sending a message). `addAgentWorkspace(provider:projectPath:)` also removes any prior uncommitted workspaces before creating a new one. Both paths currently do a bare array removal — side-state cleanup (surfaceViews, paneAgentState, etc.) will be added when the UI wiring lands in Phase 2+, since uncommitted workspaces cannot currently populate those dictionaries.

**Guards:** `splitFocused()` and `newTab()` beep and return for `.agent` workspaces (one session per workspace, v1). `liveIconKind(for:)` short-circuits to the provider's icon (`.devin`) for agent workspaces.

**Tests:** Store-dependent tests live in `WorkspaceKindTests.swift` (`@MainActor`). Pure Codable round-trip tests for the agent fields live in `WorkspaceAgentCodableTests.swift` (unannotated), following the `@MainActor` split convention documented above.

### Devin permission auto-review

`PermissionPolicy.defaultPolicy(for:)` (`Glint/Agent/PermissionReviewer.swift`) maps each `ToolKind` to `.autoApprove`, `.alwaysEscalate`, or `.llmReview`. When `WorkspaceStore.permissionReviewMode == .autoReview`, `DevinSessionManager.handlePermissionRequest` checks this policy before falling back to the manual permission overlay. `.llmReview` shells out to `devin -p -- "<prompt>"` (single-turn, non-interactive) with a prompt that ends in an unclosed JSON prefix (`{"decision":`) so the model can only continue with a valid JSON completion — `PermissionReviewer.parseResponse` re-prepends that prefix and decodes, with markdown-fence-stripping and regex-extraction fallbacks, escalating to the manual UI on any parse/timeout/process failure.

**Never overwrite `rawInput` to carry review metadata.** `RequestPermissionRequest.reviewReason` is a Glint-local field (excluded from `CodingKeys`, never encoded to or decoded from the ACP wire) added so the escalation path can attach the LLM's reasoning without destroying `rawInput` — the human reviewer must always see both the reviewer's analysis and the actual tool arguments on the permission card.

**Executable resolution:** `AgentPresence.executableURL(_:)` (`Glint/Agent/AgentHookInstaller.swift`) is the single shared resolver for locating a CLI agent binary (common GUI-safe install dirs plus `$PATH`, since a Finder-launched GUI app doesn't inherit the login shell's `PATH`). `ACPClient.devinExecutableURL()` and `PermissionReviewer`'s binary lookup both delegate to it — do not re-implement this search list again; call `AgentPresence.executableURL("devin")` (or the relevant binary name) instead.

**Tests:** Policy-only tests (no actor isolation needed) live in `PermissionPolicyTests.swift` (unannotated). `PermissionReviewer.parseResponse` tests live in `PermissionReviewerTests.swift` (`@MainActor`, since `PermissionReviewer` itself is `@MainActor`), following the same split convention as `WorkspaceKindTests.swift`/`WorkspaceAgentCodableTests.swift`.

### Devin ACP protocol integration

Glint integrates Devin through ACP v1 over the `devin acp` stdio subprocess (`Glint/Agent/ACP/ACPClient.swift`, `ACPTypes.swift`). Outbound requests use the ACP v1 shape: `protocolVersion = 1`, file read/write capabilities enabled, terminal capability disabled, `session/new`/`session/load` include `cwd` plus `mcpServers: []`, and `session/prompt.prompt` is an array of content blocks. If Devin rejects ACP v1 initialization, Glint surfaces a clear unsupported-protocol error instead of silently downgrading to an older wire format.

`ACPClient` routes newline-delimited JSON-RPC in one background stdout reader: responses resolve pending continuations by `id` (via `PendingRequest`, a lock-guarded single-resume wrapper — see below), notifications publish through `notifications`, and server requests dispatch to registered async handlers that write JSON-RPC results or errors. Malformed JSON lines are logged and ignored. Process termination, EOF, timeout, or cancellation fail affected pending continuations. Each `request(method:params:timeout:)` call races its own `timeoutTask` against the response (default 60s; `session/close` uses 2s; `session/prompt` uses 24h — a real agentic turn can legitimately run far longer than 60s, and cancellation, not a timeout, is the intended way to end one early) — do not add a second, redundant timeout layer on top of a single ACP call; if a caller needs a hard wall-clock bound across *multiple* concurrent calls, race an unstructured `Task` against a timeout `Task` and resume a shared continuation exactly once (see `WorkspaceStore.ResumeOnce`, which mirrors `ACPClient.PendingRequest`'s pattern) — a `withTaskGroup` alone does not bound execution time, since cancelling a task group's children only sets a flag and the group still awaits all of them before returning.

**Empty ACP responses:** for any request whose response body carries nothing Glint cares about (just "it didn't error"), decode as the existing `EmptyACPResult` (`ACPTypes.swift`) — e.g. `ACPClient.setMode`. Don't add another one-off `struct FooResponse { init(); init(from:) { ... tolerate null/object ... } }` type; several (`CloseSessionResponse`, `WriteTextFileResponse`, `KillTerminalResponse`, `AuthenticateResponse`) predate `EmptyACPResult` and are byte-for-byte duplicates of it — that's pre-existing debt, not a pattern to extend.

**Notification ordering (the "stuck tool call" class of bug):** `DevinSessionManager.observeNotifications` delivers `session/update` notifications via `.receive(on: DispatchQueue.main)` followed by `MainActor.assumeIsolated { self?.handleNotification(...) }` — synchronously, with no further `Task { @MainActor in ... }` hop. This isn't just style: the `session/prompt` response for the same turn resolves its own MainActor hop via a separate async chain (`Task.detached` → `await markIdle()`), and an extra unstructured-Task hop on the notification side is not guaranteed to preserve relative ordering against it. Losing that race lets a late `toolCallUpdate`/thinking notification apply *after* `markIdle()`, leaving `status` stuck busy forever with the composer permanently disabled. If you add another notification-consuming subscriber anywhere in the agent stack, keep it synchronous once already on the main queue — don't wrap it in a fresh `Task`. Separately, `DevinSessionManager.isTurnActive` gates `status` transitions driven by `applySessionUpdate` so that notifications the agent process keeps emitting for a turn the user already cancelled (`cancelTurn()`) can't flip `status` back to busy with nothing left to reset it; message/tool content from those notifications is still recorded either way.

**Tool call transcript invariants:** `DevinSessionManager.Message` intentionally preserves full ACP tool-call detail (`toolContent`, `toolLocations`, `toolRawInput`, `toolRawOutput`, timestamps, and `toolAbandonedReason`) rather than collapsing a tool call into only a display title. `mergeToolCall(...)` is the single lossless upsert path for both `tool_call` and `tool_call_update`; status-only updates commonly omit unchanged fields, so nil title/kind/content/location/raw fields must preserve the existing values. A `tool_call_update` can legally arrive before the initial `tool_call`; create a placeholder row and fill fields later. If a turn ends, fails, closes, or is cancelled while any tool call is non-terminal, `finishActiveTurn(reason:)`/`abandonUnfinishedToolCalls(reason:)` marks those tools stale instead of leaving the pane globally busy forever. The composer Stop button must call `cancelTurn()` (not `stop()`) so ACP receives `session/cancel`; `cancelTurn()` must also call `denyPendingInteractions()` so pending permission/elicitation continuations resume exactly once with the ACP `cancelled` outcome.

**Tool call UI and diagnostics:** `AgentToolCallRow` is an inspector, not a decorative status row. It should keep showing raw input/output, structured content/diffs, file locations, duration, stale reason, and copy actions when ACP provides them. Use `ACPJSONValue.prettyPrinted` for raw JSON display so objects are deterministic and top-level JSON primitives render as JSON fragments instead of Swift enum debug text. `ACPClient.diagnostics` publishes a bounded local event stream (requests, responses, notifications, server requests, stderr, malformed lines, lifecycle, errors); `DevinSessionManager.diagnostics` keeps only the recent in-memory tail for the pane diagnostics disclosure. Diagnostics are local debugging aids and are not persisted in conversation snapshots.

Devin compatibility is tolerant inbound decoding, not a second protocol mode. Glint encodes outbound `sessionId`, but accepts Devin's legacy `sessionID` alias for new-session responses, session notifications, permission/elicitation requests, file requests, and terminal requests. Unknown enum values and unknown `sessionUpdate` variants decode into `.unknown` cases so newer Devin messages don't break sessions. Per the ACP v1 spec, the `current_mode_update` notification uses a flat `modeId` key (`CurrentModeUpdate.modeId`) — distinct from `SessionModeState.currentModeId`, which is nested under `modes`/`configOptions` in session setup responses. Don't conflate the two field names.

**Permission request/response shape (was a real "stuck tool call" cause):** The ACP v1 spec's `session/request_permission` request nests tool details under `toolCall` (`{toolCallId, title?, kind?, status?, rawInput?}` — decoded here as `PermissionToolCallInfo`, deliberately more lenient than `ToolCallUpdate` since the spec's own example omits everything but `toolCallId`) and carries an `options: [PermissionOption]` array (`{optionId, name, kind}`) the agent is offering. The response **must** echo back `{"outcome": {"outcome": "selected", "optionId": "<one of the offered ids>"}}`, or `{"outcome": {"outcome": "cancelled"}}` if the client is abandoning the turn (mandatory when the user cancels/stops while a permission request is pending — see `denyPendingInteractions()`). Glint previously decoded/encoded a flat, made-up shape (`{toolCallId, title, kind}` at the top level, `{"outcome": "approved"|"denied"}` in the response) that doesn't match any real ACP wire format — Devin's ACP server has no way to act on a response like that, so approving/denying a permission card did nothing and the tool call stayed `pending` forever. `DevinSessionManager.respondToPermission(approved:)` now picks a real `optionId` from `pendingPermission?.request.options` via the static `selectOption`/`outcomeJSON` helpers; `handlePermissionRequest`'s auto-approve/auto-deny paths and the `session/request_permission` handler's `self == nil` fallback all funnel through the same helpers. `selectOption` checks `allow_once`/`reject_once` before `allow_always`/`reject_always` *by kind*, not by the offered array's order (an agent can legally list `_always` before `_once`), and returns `nil` (→ `cancelled`) rather than falling back to `options.first` when no option of the requested direction exists — falling back to an arbitrary option risked silently turning a user's Deny into an Allow (or vice versa) whenever an agent only offered one polarity. If you touch this path again, always decode/encode against the officially published schema at `https://agentclientprotocol.com/protocol/v1/tool-calls#requesting-permission` rather than assuming a shape — this is exactly the kind of guessed structure that silently produces a client that "looks" functional (shows a card, letting the user click Approve) while never actually unblocking the agent.

`selectOption`/`outcomeJSON` are `nonisolated private static func` (not instance methods) specifically so the `session/request_permission` handler's `self == nil` fallback — which runs inside a `@Sendable` async closure that is *not* `@MainActor`-isolated — can call them without needing `self` or an `await` hop. Two gotchas if you touch these again: (1) even from other instance methods of `DevinSessionManager` (which are all implicitly `@MainActor` since the class is), you must call them as `Self.selectOption(...)`/`Self.outcomeJSON(...)` — the compiler rejects a bare unqualified call to a type's own static member from an instance-method context here with a misleading "static member ... cannot be used on instance of type ..." diagnostic; and (2) leaving off `nonisolated` makes them implicitly `@MainActor`-isolated (inherited from the enclosing class), which then fails to compile at the `self == nil` fallback call site with "call to main actor-isolated static method ... in a synchronous nonisolated context" since that closure has no actor context to hop from synchronously.

**Mode switching vs. model switching:** `session/set_mode` (`{sessionId, modeId}`, confirmed by the ACP v1 spec) is implemented in `ACPClient.setMode` and wired up via `DevinSessionManager.selectMode(_:)`, which updates `currentMode` optimistically and reverts with a system message on failure. There is no confirmed ACP v1 method for the *client* to request a model change (only inbound notifications informing us of the agent's current model), so `AgentComposer`'s model control is a plain non-interactive badge, not a dropdown — don't wire up fake model-switching UI without confirming a real protocol method first.

**Prompt content and attachments:** `ACPClient.prompt(sessionID:content:)` takes `[ContentBlock]` directly; a `prompt(sessionID:text:)` convenience lives in a `DevinACPClient` extension (`content: [.text(text)]`) for simple callers. `DevinSessionManager.sendPrompt(text:projectPath:images:)` builds the content array (text block, if any, then image blocks) from `DevinSessionManager.ImageAttachment` (base64 data + MIME type). The composer's UI-facing `ComposerAttachment` (in `AgentComposer.swift`) additionally carries an `NSImage` thumbnail for display and is mapped down to `ImageAttachment` only at send time — keep that split; don't thread `NSImage` into the session manager.

`DevinSessionManager` persists conversation snapshots to `~/.glint/sessions/<workspaceID>.json` (message/tool/session metadata sufficient to render after restart). Saves are debounced ~250ms via `scheduleSave()`; assistant/thought chunks assemble by `messageId` (falling back to the latest same-role message without an id), and tool calls insert-or-replace by `toolCallId`. File handlers (`fs/read_text_file`, `fs/write_text_file`) enforce the selected project root: paths are standardized, symlinks resolved before the root check, reads must resolve to an existing non-directory file under the root, and writes validate the full resolved target (existing files) or the symlink-resolved parent directory (new files) — escapes through `..`, absolute paths, or symlinked directories/write-targets are rejected. Terminal server requests return not-implemented errors because Glint advertises `terminal = false`.

### Devin session teardown (archive, delete, quit)

Archive, delete, and app quit all route through `DevinSessionManager` teardown methods built on a shared `prepareForClose()` helper (deny pending permission/elicitation, fence the run, detach the client): `closeSessionPreservingConversation()` (archive) closes the session and synchronously flushes the debounced save so a later "Resume Session" sees the final state; `closeSessionAndDeleteConversation()` (delete) closes the session, cancels any pending debounced save, and removes the conversation file; `closeSessionForQuit()` (app quit) *awaits* the ACP `session/close` call (which already self-bounds to ~2s in `ACPClient`) instead of firing-and-forgetting, then flushes. `WorkspaceStore.deleteWorkspace` also calls the static `DevinSessionManager.deleteConversation(workspaceID:)` unconditionally for `.agent` workspaces, since a workspace restored from a prior launch whose pane was never opened this run has no live session to delegate the file removal to.

**`scheduleSave()`'s cancellation must be checked after the sleep, not assumed.** `Task.sleep` throws `CancellationError` on cancellation, but `try?` swallows that — without an explicit `guard !Task.isCancelled else { return }` right after the sleep, a "cancelled" debounced save still falls through and writes its (stale) snapshot, capable of silently resurrecting a just-deleted conversation file or clobbering a synchronous flush. If you add another cancellable delayed `Task` anywhere in this file, check `Task.isCancelled` explicitly after any `try?`-wrapped `Task.sleep` — don't rely on `.cancel()` alone.

`AppDelegate.applicationShouldTerminate` returns `.terminateLater` when `WorkspaceStore.hasLiveAgentSessions` is true, awaits `closeAllLiveAgentSessionsForQuit()`, then replies to actually terminate. `didConfirmViaWindowClose` only short-circuits the *busy-confirmation dialog* (so ⌘Q doesn't ask twice after a window-close confirmation) — it must still fall through to the graceful agent-shutdown step.

**Backlog:** Unarchiving lazily recreates the `DevinSessionManager` on next pane open, which reloads the persisted conversation from disk — there is no dedicated read-only conversation view or separate "Resume" affordance beyond the existing sidebar context-menu item. Full ACP auth-method surfacing (beyond the current heuristic keyword match on failure messages) is also not yet implemented.

### Floating glass toolbar vs. non-terminal pane content

`ContentView.floatingHeader` (`store.glassEffect`) makes `ToolbarHeader` overlay the pane area instead of pushing it down in normal layout flow (Photos-style: terminal scrollback intentionally runs *under* the glass islands). Terminal panes stay clear of the toolbar via `GhosttyManager`'s padded shell launcher, not layout insets. Any plain SwiftUI pane content (e.g. `AgentPaneView`) has no equivalent trick, so its own top-anchored content (header, etc.) must add `ToolbarHeader.height` (52pt) worth of top padding whenever `store.glassEffect` is on, or it renders underneath the floating toolbar — visually, only whatever sits below the toolbar's bottom edge peeks out, which reads as a confusing partial UI rather than an obvious full overlap. If you add another non-terminal, top-anchored SwiftUI pane, give it the same `store.glassEffect ? ToolbarHeader.height : 0` conditional inset.

### App icon preset architecture

The Dock icon picker in Settings uses a two-level model: `PortraitStyle` (line art) x `IconColorTheme` (color palette) = `AppIconPreset` (the flat enum persisted to UserDefaults). The resolution helpers on `AppIconPreset` (`portraitStyle`, `colorTheme`, `preset(portrait:color:)`) map between the two representations.

**Naming asymmetry:** The original portrait uses bare color names as raw values (`sunrise`, `classic`, `aurora`, ...), while the other portraits use `<portrait>` for their sunrise/default variant and `<portrait>-<color>` for the rest (e.g. `bun`, `bun-classic`, `bun-aurora`). The `preset(portrait:color:)` resolver handles this branching. Do not assume a uniform `<portrait>-<color>` pattern for all presets.

**To add a new portrait style:** Add the base case and all color-variant cases to `AppIconPreset`, add a case to `PortraitStyle`, update the exhaustive switches in `portraitStyle` and `colorTheme`, add the corresponding `AppIconPreset-<name>` and `GlintLogo-<name>` image sets to `Assets.xcassets`, and run `xcodegen generate`. The compiler enforces exhaustive switches, so missing a case is a build error. The round-trip tests in `AppIconPresetGroupingTests` will catch any resolution/decomposition mismatch.

**To add a new color theme:** Add the themed cases for every portrait to `AppIconPreset`, add a case to `IconColorTheme` (including `swatchColor`), update the exhaustive switches, add image sets, and run `xcodegen generate`.

## Commit & Pull Request Guidelines

Commit history uses concise Conventional Commit-style prefixes, including `fix(agent): ...`, `feat(agent): ...`, `chore: ...`, `ci: ...`, and `release: ...`. Keep commits scoped to one change. Pull requests should include a short summary, tests run, linked issues when relevant, and screenshots or recordings for visible UI changes.

## Security & Configuration Tips

Do not commit signing secrets, Sparkle private keys, notarization credentials, or generated `.secrets/` material. Release setup is documented in `docs/releasing.md`; keep signing and appcast changes isolated from feature work.
